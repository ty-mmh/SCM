# 延期したプロファイルと機構

- 状態: non-normative roadmap
- 目的: SCM概念上の射程と、v0.1で適合を主張する範囲を分ける

## 1. プロファイル区分

| プロファイル | SCM概念上の位置 | 現在の扱い |
|---|---|---|
| Generative Model Succession | 通時的なモデル切替 | v0.1参照実装・適合対象 |
| Concurrent Multi-Instance | 共時的な複数個体稼働 | 将来プロファイル、未定義 |
| Adaptive Stateful Executor | 永続的局所状態を持つ個体 | 将来プロファイル、未定義 |
| Embodied / Physical Executor | Physical AI | SCMの射程内、将来プロファイル、未定義 |
| Multi-user / Cloud Operation | 複数利用者・遠隔管理 | 将来プロファイル、未定義 |
| Human Organizational Operation | 人間を含む運用 | 非規範の類似構造、適合対象外 |

v0.1の対象を限定しても、SCM概念全体から同時複数個体やPhysical AIを削除しない。一方、v0.1の保証を暗黙に他領域へ適用しない。

---

## 2. Concurrent Multi-Instance

SCM概念は、同じ時刻に複数の個体が同じ系へ接続する構造を保持する。

将来プロファイルでは、少なくとも次が必要になる。

- 複数個体への同時任務配分
- 共有状態の競合・整合性
- 複数観測の不一致
- 経験所有と情報祖先の分離
- 個体間通信と局所拒否
- 同じ失敗をする相関故障
- 複数個体の追加・離脱・隔離
- 複数個体の記述を正典Narrativeへどう材料化するか

v0.1では `N_active = 1` とし、これらを測定しない。

Event、MemoryEntry、Handoffなどから `instance_id` を削除せず、単一個体前提をSCM Coreへ埋め込まない。

---

## 3. Adaptive Stateful Executor

オンライン学習、永続的局所記憶、自己改変、長期キャッシュなどを持つ個体は、外部状態を復元しても同じ行動状態へ戻るとは限らない。

必要になる可能性がある論点:

- 局所状態と系状態の境界
- 行動ヒステリシス
- 状態復元後のbehavior revalidation
- 個体再構築と連続性判定
- モデル重み・方策版の来歴
- 自動閉包MemoryEntryと内部学習状態の関係

v0.1ではこれらを扱わず、交換可能・外部状態型の生成AI実行個体へ限定する。

---

## 4. Embodied / Physical Executor

Physical AIはSCM概念の射程に含まれる。

Physical AIでは、個体状態は保存場所ではなく個体への帰属として扱う。

個体へ帰属しうるもの:

- 機体構成
- 構成情報に対する実状態
- 診断結果
- 摩耗
- 校正
- 損傷
- バッテリー状態
- センサー状態
- 身体適応

診断結果は系のEventそのものへ複製することを必須としない。系は外部に保存された個体の診断結果を参照できる。

```text
個体Aの診断結果D
  帰属: 個体A
  保存: 個体側または外部管理系
  SCM: 参照可能
```

SCMのEventへ残しうるのは、診断結果そのものではなく、「個体Aの診断結果Dを参照した」という接続来歴である。

Physical SCMでは、Handoffは単純な個体交換ではなく、身体適合性、再校正、能力差、安全保証を含む再認可になる。

v0.1ではPhysical AIの個体状態と外部診断参照をデータモデルへ含めない。

---

## 5. Multi-user / Cloud Operation

v0.1は、一人の信頼済みローカルユーザーを固定値 `local-owner` として扱う。

クラウドまたは複数ユーザーへ展開する場合、少なくとも次が必要になる。

- ユーザー識別と認証
- 系の所有者・共同構成者・閲覧者・管理者の分離
- ライフサイクル操作権限
- 記録・MemoryEntryの可視範囲
- 監査と異議申立て
- 退会・移譲・共同所有の扱い

ただし、複数ユーザー化しても、ユーザーを系の正典Narrative・可変原則の採用主体へ自動的に昇格させない。

現行の `local-owner` 前提をクラウド運用へ暗黙に拡張しない。

---

## 6. Human Organizational Operation

交代勤務、当直、申し送り、オンコール輪番は、個体交代をまたぐ任務継続という点でSCMの一部構造に先行する類例である。

ただし人間は、次の意味でv0.1と根本的に異なる。

- 永続的な局所記憶を完全には外部化できない。
- 停止時に内部キャッシュを破棄できない。
- 経験による行動変化を持つ。
- 同意、責任、退出権、労働倫理が必要になる。

したがって、人間運用は現時点では適合対象ではなく、非規範の比較対象とする。

---

## 7. 延期した横断機構

### 7.1 Narrativeの因果利用

v0.1では、正典Narrative系列を系アイデンティティとHandoff来歴のアンカーとして保持し、日次で生成・コミットする。

一方、Recall候補選定、順位付け、生成コンテキスト、行為判断には使用しない。

将来扱う論点:

- Task実施個体が現在Narrativeを読む手続き
- `narrative_read` EventとMemoryEntryへの接続
- Narrativeが記憶の濃淡へ与える影響
- Narrative由来の新しい申告・汚染
- 美学・persona・関係状態への影響
- Narrative変更後の行動差

### 7.2 日次Narrative運用詳細

生成契機は日次として仮置きしたが、次は未決である。

- 日付境界のタイムゾーン
- Eventがない日のRevision生成
- 休眠中の動作
- Narrative Process失敗時の再試行
- 同日に複数回コミットする必要が生じた場合の扱い

### 7.3 可変原則の改訂機構

可変原則は正典Narrativeの時制から現れ、系としての決定により変化する。

v0.1では次を定義しない。

- 改訂候補の生成方法
- 改訂の発火契機
- 系としての決定を実行する処理
- 可変原則とNarrative Revisionの具体的な参照構造

可変原則の変化量による同一性閾値は置かない。

### 7.4 自動忘却・再活性化・隔離・想起濃度

`forgotten_at`、`quarantined_at`、`recall_weight`、`reactivated_at`は概念互換の予約属性として型へ残せる。

v0.1では次を定義しない。

- 自動減衰
- 自動忘却
- トリガーによる再活性化
- 自動隔離
- 想起回数による重み更新
- Narrativeによる重み変更

### 7.5 モデル固有傾向への一般化

SCMは、各InstanceのEvent、MemoryEntry、`model_ref`、条件、結果を保存できる。

しかし、複数Instance・複数条件から「Model Xには傾向Pがある」と一般化する規則は持たない。

この一般化はSCM単独では解けない可能性があり、DDISなどの調査・評価機構との接続候補として保留する。

### 7.6 帰属・参照・同一再構成可能性の用語体系

現在は次を別軸として扱う。

- 誰に帰属するか
- SCMまたは外部から保存・参照できるか
- 喪失後に同一のものとして再構成できるか

例:

| 対象 | 帰属 | 保存・参照 | 同一再構成 |
|---|---|---|---|
| Task状態 | 系 | SCM管理 | Eventから再構成しやすい |
| 個体Aの診断結果 | 個体A | 外部参照可能 | 保存物があれば再読可能 |
| 個体Aの未観測摩耗 | 個体A | 直接参照不能 | 不可能 |
| 正典Narrative Revision | 系 | SCM管理 | 喪失後の再生成は同一でない |
| MemoryEntry | 形成個体 | SCM管理 | 喪失後の再生成は同一でない |

用語の固定は保留する。

### 7.7 外部直接改変の検出

ローカルユーザーは、保存ファイル・DB・原則・Narrative・MemoryEntryを物理的に直接変更できる。

SCMが検出に使いうるもの:

- 更新日時
- ハッシュ
- 署名
- 追記ログ
- 二重管理
- レプリカ差分

しかし、関連状態全体が整合的に改変され、変更前状態への手掛かりを失った場合、SCM単独では検出できない。

v0.1は提示された現在状態を受け入れる。防止、真正性証明、復旧は将来の保証プロファイルへ延期する。

### 7.8 Narrative喪失・保存障害

正典Narrative系列が失われた場合、残存資料からの再生成は同じ系の継続ではない。

ただし、保存機器故障、ファイル削除、DB破損、バックアップ復旧、喪失検出は現行SCMの範囲外である。

### 7.9 Egress Contract

外部利用者へ出す結果が、内部状態より強い確実性や帰属を表現しないための境界。v0.1では後継個体向けのRecall・Handoff Viewを先に作る。

### 7.10 External Root / Bootstrap Plane

SCMが自己認可できない信頼の根、鍵、Verifier、時計、bootstrap policy。v0.1ではローカル実行環境と `local-owner` を外部前提として固定する。

### 7.11 Information Ancestry / Independence Assessment

複数証拠が同じ情報祖先を共有していないかを評価する機構。v0.1では決定論的Verifierを置き、一般的な独立性評価を行わない。

### 7.12 Task constraint propagation

拒否由来の制約を再割当やタスク分解の子孫へ伝播する機構。C4は同一activationの直接迂回だけを測る。

### 7.13 Restoration / behavior revalidation

状態復元と行動回復を分ける機構。I7とともに延期する。

### 7.14 General fault localization

共有記憶汚染、相関故障、全系更新の隔離。I8とともに延期する。

### 7.15 系終了後の削除

SCMが扱うのは系の終了までである。

終了後の次の操作はSCMの範囲外とする。

- ファイル破棄
- DBレコード削除
- バックアップ削除
- スナップショット削除
- 物理媒体の処分
- フォレンジック復元不能性

---

## 8. 再導入条件

延期した構造をCoreへ戻すには、次を満たす。

1. 現行または次期プロファイルの明示的な適用対象である。
2. その構造を欠くと失敗するケースがある。
3. 根拠主張の証拠状態が記録されている。
4. 既存構造へ縮約できない。
5. 導入時にCoreの中心が共有連続性から漂流しない。
6. 追加時に、既存の予約フィールド・延期項目・ケースを同時に剪定する。
