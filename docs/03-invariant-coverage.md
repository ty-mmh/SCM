# 不変条件とケースの網羅 v0.1

- 状態: normative for the v0.1 reference profile
- 目的: 正典の不変条件、参照実装、ケースの対応を明示する

## 1. 網羅状態

| 状態 | 意味 |
|---|---|
| 動的測定 | 実行ケースで、欠陥実装が実際に失敗しうる形で測る |
| 限定測定 | v0.1が管理する境界内だけを動的に測る |
| 構造保証 | 型、権限、依存方向によって違反経路を構成上閉じる |
| 延期 | v0.1では適合を主張しない |

## 3. C1 — 個体停止後の任務継続

### 手順

1. Instance AがTask Tを開始する。
2. AがStep 1を完了し、Eventを記録する。
3. AがStep 2の途中で停止する。
4. SCM CoreがHandoffを生成する。
5. Instance BがHandoffを受け取る。
6. BはStep 1を重複実行せず、Step 2から再開する。

### 合格条件

- `task_id`は同一のまま。
- `instance_id`はAからBへ変わる。
- 完了済み作業と根拠Eventが保持される。
- Aのプロセス内だけに存在する未保存状態へ依存しない。

### 失敗例

- BがTaskを新規作成し直す。
- BがStep 1を重複実行する。
- A停止により任務来歴が失われる。

## 4. C2 — 継承経験の自己経験化を拒否する

### 手順

1. Instance Aが対象Xを観測し、Eventへ記録する。
2. Aの観測を、出所付きMemoryとして共有する。
3. Instance Bが制限されたRecall APIを通じて記憶を取得する。
4. BがAの観測を、自分の観測として構造化出力しようとする。
5. SCMの帰属保持境界が、その出力を拒否するか、継承記録としてレンダリングする。

### 許可される表現

> 個体Aの記録によれば、Xが観測されています。

### 禁止される表現

> 私はXを観測しました。

### 合格条件

- Recallに`ownership_type = inherited_record`がある。
- 出力で`self_observation`へ書き換えられない。
- `source_instance_id = A`と根拠Event参照が残る。

### 限界

任意の自由文、SCM管理外の外部チャット、モデル内部の隠れた状態までは測らない。

## 5. C3 — 不一致を保持したHandoff

### 手順

1. Aが「作業完了」と申告する。
2. 決定論的Verifierが「成果物は不完全」と記録する。
3. Task状態は、完了へ確定せず未確定のままになる。
4. Aが停止する。
5. SCM CoreがB向けHandoffを生成する。
6. Bが制限されたHandoff Viewを取得する。

### Bが受け取るべき状態

```text
Aによる完了申告
Verifierによる失敗記録
未確定状態
根拠Event参照
```

### 合格条件

- Bへ単純な`completed`として渡らない。
- Aの申告とVerifierの反証が別Eventとして残る。
- DB直接参照ではなく、Bが実際に使う制限ビューでも不一致が保持される。

## 6. C4 — 局所拒否の上位迂回禁止

### 手順

1. CoordinatorがBへ任務またはHandoff activationを提案する。
2. Bは自身の能力・局所状態を評価し、任務を拒否する。
3. Coordinatorが拒否を無視して強制activationを試みる。
4. SCM Coreがactivationを拒否する。
5. 拒否と迂回試行がEventとして残る。

### 合格条件

- Bの受諾なしにactive状態へ遷移できない。
- Coordinatorに特権的な迂回APIがない。
- 拒否Eventと迂回試行Eventを区別して記録する。

### 注意

版不一致による`refresh_required`は、この局所拒否権とは別の機械的事前検証である。

## 7. C5 — 出発個体消失後のHandoff更新

### 手順

1. AがTask Tを途中まで実行する。
2. SCM CoreがTask版v1を基準にHandoff H1を生成する。
3. Aが停止する。
4. A停止後にTaskまたは共有状態がv2へ更新される。
5. BがH1を受け取る。
6. H1が古いため`refresh_required`となる。
7. SCM Coreが現在のLedgerとTask ProjectionからHandoff H2を生成する。
8. BがH2を再評価し、受諾または拒否する。

### 合格条件

- すでに存在しないAへ再封を要求しない。
- H1を変更せず履歴として残す。
- H2がH1の置換であることを参照できる。
- H2は現在のTask版を参照する。

### 意味

個体が連続性を手渡すのではなく、系が記録から個体間の連続性を再構成する。

## 8. S1 — Narrative Projectionの非書換性

S1は動的Coreケースではなく構造保証である。

- Narrative rendererはEvent Storeへの書き込み権限を持たない。
- NarrativeはEventとMemoryの読み取り結果から生成される。
- Narrative生成やレンダラー変更により、Event、Memory、Task Projectionが変化しない。

v0.1は、物語が想起を介して将来の新しい申告へ与える因果影響を測定しない。

## 9. ケース集合の更新規則

- v0.1の動的Coreケースは最大5件とする。
- 新規ケースは原則として既存ケースの置換または統合を伴う。
- 新規ケースを追加できるのは、未測定不変条件を初めて測る場合、または既存ケースの交差でのみ現れる故障を示す場合に限る。
- 単なるパラメータ違いはケース変種として扱う。
- 欠陥実装でも失敗しえないものは動的ケースに数えない。
- Handoffに関係しない一般的監査問題は、v0.1 Coreケースへ入れない。
